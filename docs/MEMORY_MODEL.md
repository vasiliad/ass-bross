# МОДЕЛЬ ПАМЯТИ И СТРУКТУРЫ ДАННЫХ
**Проект:** Сверхлегкий веб-браузер (NanoWeb)
**Платформа:** Windows 10/11 x64

Все структуры выравниваются по границе 8 байт. Числовые поля, не являющиеся указателями, по умолчанию `dword` (знаковые 32-битные), указатели — `qword`.

> Единственный источник истины по смещениям — файл `src/include/structs.inc` (макрос `struct ... ends` из пакета FASM). Таблицы ниже — документация к нему; при изменении структуры обновляются оба места. Писать в коде «магические» смещения вида `[rbx+0x18]` запрещено — только `[rbx+DOM_NODE.Last_Child]`.

## 1. Арены памяти (Arena Allocator)

### 1.1. Принцип
Память запрашивается у ОС через `VirtualAlloc`:
1. **Резервирование** большого диапазона виртуальных адресов (`MEM_RESERVE`) — физическая память не расходуется.
2. **Фиксация** (`MEM_COMMIT`) по мере роста арены шагами по 64 КБ.

Жёсткого лимита размера нет, а реальное потребление равно реально использованному объёму. Адреса внутри арены **никогда не перемещаются** — сырые указатели остаются валидными, а арена может служить растущим непрерывным буфером.

Отдельные объекты не освобождаются. Арена освобождается целиком: `arena_reset` (указатель возвращается в начало, лишняя память декоммитится) или `arena_release` (`VirtualFree(MEM_RELEASE)`), за `O(1)` относительно числа объектов.

### 1.2. Заголовок арены (ARENA), 32 байта
```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Base           ; Начало зарезервированного диапазона
+0x08     qword    Ptr            ; Текущая позиция выделения
+0x10     qword    Commit_End     ; Граница зафиксированной памяти
+0x18     qword    Reserve_End    ; Граница зарезервированного диапазона
```

### 1.3. API
| Функция | Аргументы | Результат |
|---|---|---|
| `arena_init` | `rcx` = ARENA*, `rdx` = размер резерва | `rax` = 1 / 0 при ошибке |
| `arena_alloc` | `rcx` = ARENA*, `rdx` = размер | `rax` = указатель (выровнен на 8, **обнулён**) или 0 |
| `arena_append` | `rcx` = ARENA*, `rdx` = данные, `r8` = длина | `rax` = 1 / 0 (дописать байты в конец без выравнивания — для буферов загрузки) |
| `arena_reset` | `rcx` = ARENA* | — |
| `arena_release` | `rcx` = ARENA* | — |

Память из `arena_alloc` всегда обнулена (свежие страницы ОС нулевые; после `arena_reset` память декоммитится, поэтому повторная фиксация тоже даёт нули).

### 1.4. Набор арен
| Арена | Время жизни | Резерв (виртуальный) | Что хранит |
|---|---|---|---|
| `src_arena` | Документ | 64 МБ | Байты HTML-страницы как один непрерывный буфер |
| `doc_arena` | Документ | 256 МБ | DOM_NODE, ATTR, HIDE_RULE, SEL_PART, IMAGE, декодированные строки |
| `layout_arena` | До следующего relayout | 64 МБ | FRAGMENT |
| `line_arena` | До следующего relayout | 32 МБ | Массив LINE (непрерывный, сверху вниз) |
| `scratch_arena` | Одна операция | 16 МБ | Временные буферы (UTF-16 для GDI, URL и т.п.) |
| Арена ресурса | До разбора ресурса / документ | 16 МБ каждая | Сжатые байты одной внешней таблицы стилей или одной картинки |

Каждый внешний ресурс (таблица стилей, картинка) загружается в **собственную** маленькую арену: загрузки идут параллельно, и каждой нужен свой непрерывный буфер. Арена таблицы стилей освобождается сразу после извлечения правил скрытия; арена картинки живёт вместе с документом (из неё картинка декодируется повторно).

При изменении размера окна сбрасываются `layout_arena` и `line_arena`, DOM не трогается. При навигации освобождаются все арены документа и ресурсов.

### 1.5. Пиксели картинок
Распакованные пиксели — единственные данные, которые освобождаются поштучно, поэтому они живут **вне арен**: отдельный `VirtualAlloc` на каждую картинку, `VirtualFree` при вытеснении.
* Формат: 32 бита BGRA с premultiplied alpha, размер уже уменьшен до отображаемого (не больше ширины колонки × DPI).
* **Бюджет кэша — 6 МБ.** При превышении вытесняются картинки, дальше всего отстоящие от видимой области (по `Last_Used`). Вытесненная картинка при возврате к ней декодируется заново из своей арены.

## 2. Строки
* Строки хранятся как **срез**: пара `указатель (qword) + длина (dword)`, без завершающего нуля.
* По возможности срез указывает прямо в `src_arena` (zero-copy). Если текст преобразован (декодирование `&amp;`, приведение регистра) — копия кладётся в `doc_arena`.
* Внутренняя кодировка — **UTF-8**. Документы в `windows-1251` перекодируются при загрузке. В UTF-16 строки переводятся только на границе с WinAPI, в `scratch_arena`.
* Имена тегов и атрибутов ASCII-регистронезависимы. Известные имена переводятся в числовые идентификаторы (`TAG_DIV`, `ATTR_HREF`, …) совершенным хэшем по таблицам из `src/data/`.

## 3. Узел DOM (DOM_NODE)
Размер: 64 байта (`0x40`). Арена: `doc_arena`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     dword    Node_Type      ; 0=Element, 1=Text, 2=Comment, 3=Document
+0x04     dword    Flags          ; Битовые флаги (см. ниже)
+0x08     qword    Parent         ; Родительский DOM_NODE
+0x10     qword    First_Child    ; Первый ребенок
+0x18     qword    Last_Child     ; Последний ребенок (добавление ребенка за O(1))
+0x20     qword    Next_Sibling   ; Следующий соседний узел
+0x28     dword    Tag_ID         ; TAG_* для элементов; TAG_UNKNOWN для незнакомых; 0 для текста
+0x2C     dword    Data_Len       ; Длина Data_Ptr в байтах
+0x30     qword    Data_Ptr       ; Element: имя тега из исходника; Text/Comment: содержимое (UTF-8)
+0x38     qword    First_Attr     ; Первый ATTR (связный список), 0 если атрибутов нет
```

Роль элемента в режиме чтения не хранится: она берётся из статической таблицы по `Tag_ID` (`ARCHITECTURE.md`, раздел 6).

Флаги (`Flags`):
| Бит | Имя | Значение |
|---|---|---|
| 0 | `NF_WHITESPACE_ONLY` | Текстовый узел состоит только из пробельных символов |
| 1 | `NF_VOID` | Void-элемент или `<x/>` |
| 2 | `NF_HIDDEN` | Элемент скрыт (атрибут `hidden`/`aria-hidden`, `style`, правило скрытия) — вместе с потомками |

## 4. Атрибут (ATTR)
Размер: 32 байта. Арена: `doc_arena`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий атрибут элемента
+0x08     qword    Name_Ptr       ; Имя атрибута (в исходнике)
+0x10     qword    Value_Ptr      ; Значение (сущности уже декодированы)
+0x18     dword    Name_Len
+0x1C     dword    Value_Len
```

## 5. Правила скрытия (HIDE_RULE, SEL_PART)
Арена: `doc_arena`. Хранятся только правила, которые скрывают элементы (`display: none`, `visibility: hidden`); остальные правила CSS сайта не сохраняются.

### 5.1. HIDE_RULE, 16 байт
```text
+0x00     qword    Next           ; Следующее правило в той же корзине
+0x08     qword    Selector       ; SEL_PART самой правой части селектора
```
Правила раскладываются по корзинам хэш-таблицы по самой правой части селектора: отдельно по `#id`, `.class`, тегу и корзина «прочие» (`*`). Для элемента проверяются только корзины его id, его классов и его тега. Селектор вида `.a, .b` разворачивается в два правила.

### 5.2. SEL_PART, 40 байт
Цепочка хранится справа налево — сопоставление идёт от элемента вверх к предкам.
```text
+0x00     qword    Next           ; Часть левее (предок / родитель)
+0x08     dword    Tag_ID         ; 0 = любой тег (*)
+0x0C     dword    Combinator     ; Связь с частью Next: 0=нет, 1=потомок (пробел), 2=ребенок (>)
+0x10     qword    Id_Ptr         ; #id или 0
+0x18     dword    Id_Len
+0x1C     dword    Class_Len
+0x20     qword    Class_Ptr      ; .class или 0 (один класс на часть)
```

## 6. Картинка (IMAGE)
Размер: 96 байт (`0x60`). Арена: `doc_arena`. Одна запись на каждый `<img>` документа.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующая картинка документа (в порядке документа)
+0x08     qword    Node           ; DOM_NODE элемента <img>
+0x10     qword    Url_Ptr        ; Абсолютный URL (после выбора src / data-src / srcset)
+0x18     dword    Url_Len
+0x1C     dword    State          ; 0=Ожидает, 1=Загружается, 2=Загружена, 3=Декодирована, 4=Ошибка
+0x20     ARENA    Data           ; Собственная арена со сжатыми байтами файла (32 байта)
+0x40     dword    Natural_W      ; Размер оригинала (из width/height или заголовка файла)
+0x44     dword    Natural_H
+0x48     dword    Display_W      ; Размер на экране (после вписывания в колонку и DPI)
+0x4C     dword    Display_H
+0x50     qword    Pixels         ; BGRA premultiplied (VirtualAlloc) или 0, если не декодирована / вытеснена
+0x58     dword    Last_Used      ; Номер кадра последней отрисовки (для вытеснения)
+0x5C     dword    Reserved
```

## 7. Строка раскладки (LINE)
Размер: 32 байта. Арена: `line_arena` — **непрерывный массив** в порядке сверху вниз (Y возрастает). Поэтому видимая строка и строка под курсором находятся двоичным поиском по `Y`.

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     qword    First_Fragment   ; Первый FRAGMENT строки (0 для линии <hr>)
+0x08     dword    Y                ; Верх строки в координатах документа
+0x0C     dword    Height
+0x10     dword    Baseline         ; Смещение базовой линии от Y
+0x14     dword    X                ; Левый край содержимого с учётом отступа (списки, цитаты)
+0x18     dword    Quote_Depth      ; Сколько полос цитаты рисовать слева
+0x1C     dword    Kind             ; 0=Текст, 1=Линия <hr>, 2=Блочная картинка
```

## 8. Фрагмент (FRAGMENT)
Размер: 48 байт (`0x30`). Арена: `layout_arena`. Кусок строки с одинаковым оформлением: слово или несколько слов, маркер списка или картинка.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий фрагмент этой строки
+0x08     qword    Data           ; FR_IMAGE: IMAGE*; иначе — текст UTF-8
+0x10     qword    Link           ; DOM_NODE ссылки <a>, к которой относится фрагмент, или 0
+0x18     dword    Text_Len       ; Длина текста (0 для картинки)
+0x1C     dword    Font_ID        ; Индекс в таблице шрифтов SysFont (размер × начертание)
+0x20     dword    X
+0x24     dword    Width          ; Высота и вертикальное положение — из LINE
+0x28     dword    Flags          ; FR_LINK, FR_UNDERLINE, FR_STRIKE, FR_IMAGE, FR_MUTED, FR_MARKER
+0x2C     dword    Reserved
```

Выделение найденного по Ctrl+F хранится отдельно (список «строка + смещение + длина» в `scratch_arena`), раскладка при поиске не меняется.

## 9. Оценка потребления
| Сущность | Размер | На 1000 элементов |
|---|---|---|
| DOM_NODE | 64 Б | 62 КБ |
| ATTR (≈2 на элемент) | 32 Б | 62 КБ |
| LINE + FRAGMENT (≈1 строка и 3 фрагмента на элемент) | 32 + 3×48 Б | 172 КБ |

Итого около 300 КБ на 1000 элементов без учёта текста, исходника и картинок. Картинки ограничены бюджетом кэша пикселей в 6 МБ (раздел 1.5) плюс сжатые файлы.
