# МОДЕЛЬ ПАМЯТИ И СТРУКТУРЫ ДАННЫХ
**Проект:** Сверхлегкий веб-браузер (NanoWeb)
**Платформа:** Windows 10/11 x64

Все структуры выравниваются по границе 8 байт. Числовые поля, не являющиеся указателями, по умолчанию `dword` (знаковые 32-битные), указатели — `qword`.

> Единственный источник истины по смещениям — файл `src/include/structs.inc` (макрос `struct ... ends` из пакета FASM). Таблицы ниже — документация к нему; при изменении структуры обновляются оба места. Писать в коде «магические» смещения вида `[rbx+0x18]` запрещено — только `[rbx+DOM_NODE.Last_Child]`.

## 1. Арены памяти (Arena Allocator)

### 1.1. Принцип
Память запрашивается у ОС через `VirtualAlloc`:
1. **Резервирование** большого диапазона виртуальных адресов (`MEM_RESERVE`) — физическая память не расходуется.
2. **Фиксация** (`MEM_COMMIT`) по мере роста арены шагами по 64 КБ.

Благодаря этому арена не имеет жёсткого лимита в 16 МБ, но реальное потребление памяти равно реально использованному объёму. Адреса внутри арены **никогда не перемещаются** — сырые указатели между узлами остаются валидными.

Отдельные объекты не освобождаются. Арена освобождается целиком: `arena_reset` (указатель возвращается в начало, лишняя память декоммитится) или `arena_release` (`VirtualFree(MEM_RELEASE)`), обе операции за `O(1)` относительно числа объектов.

### 1.2. Заголовок арены (ARENA), 32 байта
```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Base           ; Начало зарезервированного диапазона
+0x08     qword    Ptr            ; Текущая позиция выделения
+0x10     qword    Commit_End     ; Граница зафиксированной памяти
+0x18     qword    Reserve_End    ; Граница зарезервированного диапазона
```

### 1.3. API
| Функция | Аргументы | Результат |
|---|---|---|
| `arena_init` | `rcx` = ARENA*, `rdx` = размер резерва | `rax` = 1 / 0 при ошибке |
| `arena_alloc` | `rcx` = ARENA*, `rdx` = размер | `rax` = указатель (выровнен на 8, **обнулён**) или 0 |
| `arena_reset` | `rcx` = ARENA* | — |
| `arena_release` | `rcx` = ARENA* | — |

Память из `arena_alloc` всегда обнулена (свежие страницы ОС уже нулевые; после `arena_reset` память декоммитится, поэтому повторная фиксация тоже даёт нули). Код может полагаться на то, что все поля новой структуры равны 0.

### 1.4. Набор арен
| Арена | Время жизни | Резерв (виртуальный) | Что хранит |
|---|---|---|---|
| `src_arena` | Документ (вкладка) | 64 МБ | Сырые байты HTTP-ответа / файла как один непрерывный буфер |
| `doc_arena` | Документ (вкладка) | 256 МБ | DOM_Node, ATTR, COMPUTED_STYLE, CSSOM, декодированные строки |
| `layout_arena` | До следующего relayout | 64 МБ | RENDER_BOX, TEXT_FRAGMENT |
| `scratch_arena` | Одна операция | 16 МБ | Временные буферы (UTF-16 для GDI, разбор URL и т.п.) |

`src_arena` используется как растущий байтовый буфер: сеть дописывает данные в конец, адрес начала не меняется. Поэтому токенизатор может ссылаться на исходный текст напрямую, а токены на границах сетевых пакетов не разрываются.

При изменении размера окна выполняется `arena_reset(layout_arena)` и полный пересчёт компоновки — DOM и стили не трогаются. При навигации на новую страницу сбрасываются все три арены документа.

## 2. Строки

* Строки хранятся как **срез**: пара `указатель (qword) + длина (dword)`, без завершающего нуля.
* По возможности срез указывает прямо в `src_arena` (zero-copy). Если текст пришлось преобразовать (декодирование `&amp;`, приведение регистра) — копия кладётся в `doc_arena`.
* Внутренняя кодировка — **UTF-8**. Документы в `windows-1251` перекодируются в UTF-8 при загрузке (`MultiByteToWideChar` → `WideCharToMultiByte`). В UTF-16 строки переводятся только на границе с GDI, в `scratch_arena`.
* Имена тегов, атрибутов и CSS-свойств ASCII-регистронезависимы. Известные имена переводятся в числовые идентификаторы (`TAG_DIV`, `PROP_COLOR`, …) по статическим таблицам из `src/data/`; сравнение идентификаторов — одна инструкция `cmp`.

## 3. Структура узла DOM (DOM_NODE)
Размер: 72 байта (`0x48`). Арена: `doc_arena`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     dword    Node_Type      ; 0=Element, 1=Text, 2=Comment, 3=Document
+0x04     dword    Flags          ; Битовые флаги (см. ниже)
+0x08     qword    Parent         ; Родительский DOM_NODE
+0x10     qword    First_Child    ; Первый ребенок
+0x18     qword    Last_Child     ; Последний ребенок (добавление ребенка за O(1))
+0x20     qword    Next_Sibling   ; Следующий соседний узел
+0x28     dword    Tag_ID         ; TAG_* для элементов; TAG_UNKNOWN для незнакомых; 0 для текста
+0x2C     dword    Data_Len       ; Длина Data_Ptr в байтах
+0x30     qword    Data_Ptr       ; Element: имя тега из исходника; Text/Comment: содержимое (UTF-8)
+0x38     qword    First_Attr     ; Первый ATTR (связный список), 0 если атрибутов нет
+0x40     qword    Style          ; COMPUTED_STYLE*, заполняется на этапе Style Resolve
```

Флаги (`Flags`):
| Бит | Имя | Значение |
|---|---|---|
| 0 | `NF_WHITESPACE_ONLY` | Текстовый узел состоит только из пробельных символов |
| 1 | `NF_SELF_CLOSING` | Элемент записан как `<x/>` или является void-элементом (`br`, `img`, `meta`…) |
| 2 | `NF_LINK` | Элемент `<a href>` — участвует в hit-testing |

## 4. Атрибут (ATTR)
Размер: 32 байта. Арена: `doc_arena`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий атрибут элемента
+0x08     qword    Name_Ptr       ; Имя атрибута (в исходнике, сравнивать без учета регистра)
+0x10     qword    Value_Ptr      ; Значение (сущности уже декодированы)
+0x18     dword    Name_Len
+0x1C     dword    Value_Len
```

## 5. Вычисленный стиль (COMPUTED_STYLE)
Размер: 88 байт (`0x58`). Арена: `doc_arena`. Создаётся для каждого элемента; текстовые узлы используют стиль родителя.

Длины хранятся в пикселях (CSS px, до DPI-масштабирования). `em` пересчитываются в px при вычислении стиля. Специальное значение `AUTO = 0x80000000`.

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     dword    Display          ; 0=Block, 1=Inline, 2=None, 3=List_Item
+0x04     dword    Color            ; Цвет текста, ARGB
+0x08     dword    Background       ; Цвет фона, ARGB (A=0 — прозрачный)
+0x0C     dword    Font_Size        ; px
+0x10     dword    Font_Weight      ; 400 / 700
+0x14     dword    Width            ; px, % или AUTO (см. Flags)
+0x18     dword    Height           ; px или AUTO
+0x1C     dword    Text_Align       ; 0=Left, 1=Center, 2=Right
+0x20     dword[4] Margin           ; Top, Right, Bottom, Left
+0x30     dword[4] Padding          ; Top, Right, Bottom, Left
+0x40     dword[4] Border_Width     ; Top, Right, Bottom, Left
+0x50     dword    Border_Color     ; ARGB
+0x54     dword    Flags            ; Бит 0: Width в процентах; бит 1: italic; бит 2: underline
```

## 6. CSSOM
Арена: `doc_arena`. В MVP правила хранятся связным списком в порядке появления; индексация по тегу/классу/id хэш-таблицами — оптимизация после MVP.

### 6.1. Правило (CSS_RULE), 32 байта
```text
+0x00     qword    Next           ; Следующее правило
+0x08     qword    Selector       ; SEL_PART самой правой части селектора
+0x10     qword    First_Decl     ; Первая CSS_DECL
+0x18     dword    Specificity    ; (a<<16)|(b<<8)|c
+0x1C     dword    Order          ; Порядковый номер в источнике (UA-стили первыми)
```
Селектор вида `div p, h1` разворачивается в несколько правил с одинаковыми объявлениями.

### 6.2. Часть селектора (SEL_PART), 40 байт
Цепочка хранится справа налево — так сопоставление идёт от элемента вверх к предкам.
```text
+0x00     qword    Next           ; Часть левее (предок / родитель)
+0x08     dword    Tag_ID         ; 0 = любой тег (*)
+0x0C     dword    Combinator     ; Связь с частью Next: 0=нет, 1=потомок (пробел), 2=ребенок (>)
+0x10     qword    Id_Ptr         ; #id или 0
+0x18     dword    Id_Len
+0x1C     dword    Class_Len
+0x20     qword    Class_Ptr      ; .class или 0 (в MVP — один класс на часть)
```

### 6.3. Объявление (CSS_DECL), 24 байта
```text
+0x00     qword    Next
+0x08     dword    Prop_ID        ; PROP_*
+0x0C     dword    Flags          ; Бит 0: !important
+0x10     dword    Value          ; Число, ARGB или KW_* (ключевое слово)
+0x14     dword    Unit           ; 0=px, 1=%, 2=em, 3=color, 4=keyword
```
Сокращённые свойства (`margin: 0 auto`, `border: 1px solid red`) разворачиваются в отдельные объявления ещё при разборе.

## 7. Блок компоновки (RENDER_BOX)
Размер: 64 байта (`0x40`). Арена: `layout_arena`. Формирует **Render Tree**.

Координаты — абсолютные, в системе координат документа (border-box). Прокрутка учитывается только на этапе отрисовки вычитанием `scroll_y`, поэтому скролл не требует пересчёта компоновки.

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     qword    Node             ; DOM_NODE* (0 для анонимных блоков и строк)
+0x08     qword    Parent           ; Родительский RENDER_BOX
+0x10     qword    First_Child      ; Первый дочерний RENDER_BOX
+0x18     qword    Next_Sibling     ; Следующий RENDER_BOX
+0x20     dword    X
+0x24     dword    Y
+0x28     dword    Width
+0x2C     dword    Height
+0x30     dword    Box_Type         ; 0=Block, 1=Anonymous_Block, 2=Line
+0x34     dword    Flags
+0x38     qword    First_Fragment   ; Для Box_Type=Line: первый TEXT_FRAGMENT
```

Правило построения: блок содержит **либо** только блочных детей, **либо** только строки. Если внутри блока смешаны блочные и строчные элементы, строчные заворачиваются в `Anonymous_Block`. Цвета и отступы не дублируются — отрисовщик берёт их из `Node → Style`.

## 8. Фрагмент текста (TEXT_FRAGMENT)
Размер: 48 байт (`0x30`). Арена: `layout_arena`. Кусок текста, целиком помещающийся на одной строке.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий фрагмент в этой строке
+0x08     qword    Style          ; COMPUTED_STYLE* (шрифт, цвет, подчеркивание)
+0x10     qword    Text_Ptr       ; Срез UTF-8 внутри текстового узла
+0x18     dword    Text_Len
+0x1C     dword    X
+0x20     dword    Y
+0x24     dword    Width
+0x28     dword    Height
+0x2C     dword    Reserved       ; Выравнивание до 8 байт
```

> В MVP фон и рамки строчных элементов (`<span style="background:…">`) не рисуются — только цвет и начертание текста.

## 9. Оценка потребления
| Сущность | Размер | На 1000 элементов |
|---|---|---|
| DOM_NODE | 72 Б | 70 КБ |
| COMPUTED_STYLE | 88 Б | 86 КБ |
| RENDER_BOX | 64 Б | 62 КБ |
| ATTR (≈2 на элемент) | 32 Б | 62 КБ |

Итого порядка 300 КБ на 1000 элементов без учёта текста и исходника — в рамках KPI «< 1 МБ на 1000 узлов».
