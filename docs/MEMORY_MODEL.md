# МОДЕЛЬ ПАМЯТИ И СТРУКТУРЫ ДАННЫХ
**Проект:** Сверхлегкий веб-браузер (NanoWeb)
**Платформа:** Windows 10/11 x64

Все структуры выравниваются по границе 8 байт. Числовые поля, не являющиеся указателями, по умолчанию `dword` (знаковые 32-битные), указатели — `qword`.

> Единственный источник истины по смещениям — файл `src/include/structs.inc` (макрос `struct ... ends` из пакета FASM). Таблицы ниже — документация к нему; при изменении структуры обновляются оба места, а размер проверяется утверждением при сборке. Писать в коде «магические» смещения вида `[rbx+0x18]` запрещено — только `[rbx+DOM_NODE.Last_Child]`.

## 1. Арены памяти (Arena Allocator)

### 1.1. Принцип
Память запрашивается у ОС через `VirtualAlloc`:
1. **Резервирование** большого диапазона виртуальных адресов (`MEM_RESERVE`) — физическая память не расходуется.
2. **Фиксация** (`MEM_COMMIT`) по мере роста арены шагами `Commit_Step` (64 КБ для арен документа, 4 КБ для арен ресурсов).

Жёсткого лимита размера нет, реальное потребление равно реально использованному объёму. Адреса внутри арены **никогда не перемещаются** — сырые указатели остаются валидными, а арена может служить растущим непрерывным буфером.

Отдельные объекты не освобождаются. Арена освобождается целиком — `arena_reset` или `arena_release`.

### 1.2. Заголовок арены (ARENA), 40 байт
```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Base           ; Начало зарезервированного диапазона
+0x08     qword    Ptr            ; Текущая позиция выделения
+0x10     qword    Commit_End     ; Граница зафиксированной памяти
+0x18     qword    Reserve_End    ; Граница зарезервированного диапазона
+0x20     dword    Commit_Step    ; Шаг фиксации в байтах (кратен 4 КБ)
+0x24     dword    Flags          ; Зарезервировано
```

### 1.3. API
| Функция | Аргументы | Результат |
|---|---|---|
| `arena_init` | `rcx` = ARENA*, `rdx` = размер резерва, `r8d` = шаг фиксации | `rax` = 1 / 0 при ошибке |
| `arena_alloc` | `rcx` = ARENA*, `rdx` = размер | `rax` = указатель (выровнен на 8, **обнулён**) или 0 |
| `arena_ensure` | `rcx` = ARENA*, `rdx` = сколько байт должно быть свободно и зафиксировано после `Ptr` | `rax` = указатель на `Ptr` или 0 (для приёма данных из сети: память фиксируется **до** `WinHttpReadData`) |
| `arena_advance` | `rcx` = ARENA*, `rdx` = сколько байт записано | — (сдвигает `Ptr` после записи через `arena_ensure`) |
| `arena_reset` | `rcx` = ARENA* | — |
| `arena_release` | `rcx` = ARENA* | — |

**Инвариант обнулённости.** Память из `arena_alloc` всегда нулевая. `arena_reset` обеспечивает это так:
* первый блок (`Commit_Step` байт от `Base`) остаётся зафиксированным, его **использованная часть обнуляется** (`rep stosq` до `min(Ptr, Base + Commit_Step)`);
* всё выше первого блока **декоммитится** (`VirtualFree(MEM_DECOMMIT)`); повторная фиксация даёт свежие нулевые страницы ОС.

Так частые сбросы маленькой арены (`scratch`) обходятся без системных вызовов, а большие сбросы не держат память. `MEM_RESET` не используется — он не гарантирует нулей.

### 1.4. Набор арен
| Арена | Время жизни | Резерв | Шаг | Что хранит |
|---|---|---|---|---|
| `src` | Документ | 64 МБ | 64 КБ | Текст HTML-страницы в UTF-8 — один непрерывный буфер |
| `doc` | Документ | 256 МБ | 64 КБ | DOM_NODE, ATTR, VIS_RULE, SEL_PART, IMAGE, декодированные строки, корзины правил |
| `text` | До relayout | 32 МБ | 64 КБ | Нормализованный текст видимого содержимого (раздел 7) |
| `layout` | До relayout | 64 МБ | 64 КБ | FRAGMENT |
| `line` | До relayout | 32 МБ | 64 КБ | Массив LINE |
| `find` | До нового поиска / relayout | 4 МБ | 64 КБ | Совпадения Ctrl+F |
| `scratch` | Одна операция | 16 МБ | 64 КБ | Временные буферы (UTF-16 для WinAPI, URL, заголовки) |
| `session` | Процесс | 64 МБ | 64 КБ | Настройки, шаблоны поиска, история (HISTORY_ENTRY), URL и заголовки страниц истории |
| Арена ресурса | Ресурс | 16 МБ каждая | 4 КБ | Сырые байты одного ресурса: таблицы стилей, картинки или HTML в кодировке, отличной от UTF-8 |
| Арена кэша страницы | До вытеснения из истории | по размеру | 64 КБ | Копия текста страницы (UTF-8) для мгновенного «Назад» |

Арены `src`, `doc`, `text`, `layout`, `line` принадлежат **контексту документа** (`DOC_CTX`, раздел 3). Ресурсы получают собственные арены: загрузки идут параллельно, и каждой нужен свой непрерывный буфер. При известном `Content-Length` вызывается `arena_ensure` на весь размер сразу; шаг 4 КБ не даёт сотне мелких иконок занять мегабайты.

### 1.5. Пиксели картинок
Распакованные пиксели — единственные данные, которые освобождаются поштучно, поэтому они живут **вне арен**: отдельный `VirtualAlloc` на каждую картинку, `VirtualFree` при вытеснении.
* Формат: 32 бита BGRA с premultiplied alpha, размер уже уменьшен до отображаемого.
* **Бюджет кэша = 6 МБ × (масштаб DPI)²** (при 100% — 6 МБ, при 150% — 13,5 МБ, при 200% — 24 МБ).
* Вытесняются картинки, дальше всего отстоящие от видимой области. Картинки, видимые прямо сейчас, не вытесняются никогда — даже если временно превышают бюджет.
* Вытесненная картинка декодируется заново из своей арены ресурса.

## 2. Строки
* Строки хранятся как **срез**: пара `указатель (qword) + длина (dword)`, без завершающего нуля.
* По возможности срез указывает прямо в `src` (zero-copy). Если текст преобразован (декодирование `&amp;`, приведение регистра) — копия кладётся в `doc`.
* Внутренняя кодировка — **UTF-8**. Документ в другой кодировке загружается в арену ресурса, перекодируется в `src` (`ARCHITECTURE.md`, раздел 3), после чего арена ресурса освобождается. UTF-8-документ пишется в `src` напрямую. В UTF-16 строки переводятся только на границе с WinAPI, в `scratch`.
* Имена тегов и атрибутов ASCII-регистронезависимы. Известные имена переводятся в числовые идентификаторы (`TAG_DIV`, `ATTR_HREF`, …) совершенным хэшем по таблицам из `src/data/`.

## 3. Контекст документа (DOC_CTX)
Размер: 256 байт (`0x100`). Статический пул из **3 слотов** (текущий документ, документ в процессе закрытия, запас). Нужен потому, что после навигации старый документ нельзя освободить, пока WinHTTP не подтвердит закрытие всех его запросов (`ARCHITECTURE.md`, раздел 5.2).

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     ARENA    Src
+0x28     ARENA    Doc
+0x50     ARENA    Text
+0x78     ARENA    Layout
+0xA0     ARENA    Line
+0xC8     qword    Root             ; DOM_NODE типа Document
+0xD0     qword    First_Image      ; Первая IMAGE документа
+0xD8     qword    Rule_Buckets     ; Таблица корзин VIS_RULE (в Doc)
+0xE0     qword    Url_Ptr          ; Итоговый URL после редиректов (в Doc) — база для относительных ссылок
+0xE8     dword    Url_Len
+0xEC     dword    In_Flight        ; Число незакрытых FETCH этого документа
+0xF0     dword    State            ; 0=Свободен, 1=Загружается, 2=Готов, 3=Закрывается
+0xF4     dword    Charset          ; CS_UTF8, CS_1251, CS_1252, CS_KOI8R
+0xF8     dword    Scroll_Y
+0xFC     dword    Generation       ; Номер навигации
```

## 4. Узел DOM (DOM_NODE)
Размер: 72 байта (`0x48`). Арена: `doc`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     dword    Node_Type      ; 0=Element, 1=Text, 2=Comment, 3=Document (DOCTYPE отбрасывается)
+0x04     dword    Flags          ; Битовые флаги (см. ниже)
+0x08     qword    Parent         ; Родительский DOM_NODE
+0x10     qword    First_Child    ; Первый ребенок
+0x18     qword    Last_Child     ; Последний ребенок (добавление ребенка за O(1))
+0x20     qword    Next_Sibling   ; Следующий соседний узел
+0x28     dword    Tag_ID         ; TAG_* для элементов; TAG_UNKNOWN для незнакомых; 0 для текста
+0x2C     dword    Data_Len       ; Длина Data_Ptr в байтах
+0x30     qword    Data_Ptr       ; Element: имя тега из исходника; Text/Comment: содержимое (UTF-8)
+0x38     qword    First_Attr     ; Первый ATTR (связный список), 0 если атрибутов нет
+0x40     dword    Line_Index     ; Индекс первой LINE элемента в массиве строк; -1 если не отображается
+0x44     dword    Order          ; Порядковый номер узла в документе (якорь прокрутки для истории)
```

Узлы только добавляются, никогда не удаляются и не перемещаются (`Prev_Sibling` не нужен). Роль элемента берётся из статической таблицы по `Tag_ID` (`ARCHITECTURE.md`, раздел 6).

Флаги (`Flags`):
| Бит | Имя | Значение |
|---|---|---|
| 0 | `NF_WHITESPACE_ONLY` | Текстовый узел состоит только из пробельных символов |
| 1 | `NF_VOID` | Void-элемент или `<x/>` |
| 2 | `NF_HIDDEN` | Элемент скрыт по итогу правил видимости — вместе с потомками. Пересчитывается при изменении ширины окна |
| 3 | `NF_HIDDEN_ATTR` | Скрыт атрибутом `hidden` / `aria-hidden="true"` (не зависит от ширины окна) |
| 4 | `NF_HAS_ID` | У элемента есть атрибут `id` (ускоряет поиск якоря) |

## 5. Атрибут (ATTR)
Размер: 40 байт (`0x28`). Арена: `doc`.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий атрибут элемента
+0x08     qword    Name_Ptr       ; Имя атрибута (в исходнике)
+0x10     qword    Value_Ptr      ; Значение (сущности уже декодированы)
+0x18     dword    Name_Len
+0x1C     dword    Value_Len
+0x20     dword    Attr_ID        ; ATTR_* (совершенный хэш) или ATTR_UNKNOWN
+0x24     dword    Reserved
```

## 6. Правила видимости (VIS_RULE, SEL_PART)
Арена: `doc`. Из CSS сайта сохраняются только правила, влияющие на видимость: скрывающие (`display: none`, `visibility: hidden`) и показывающие (`display:` любое другое значение, `visibility: visible`). Решение для элемента — по упрощённому каскаду (`ARCHITECTURE.md`, раздел 7).

### 6.1. VIS_RULE, 40 байт
```text
+0x00     qword    Next           ; Следующее правило в той же корзине
+0x08     qword    Selector       ; SEL_PART самой правой части селектора
+0x10     dword    Order          ; Порядковый номер правила в документе (с учётом порядка таблиц стилей)
+0x14     dword    Specificity    ; (id << 16) | (class << 8) | tag
+0x18     dword    Effect         ; 0=Скрыть, 1=Показать
+0x1C     dword    Flags          ; Бит 0: !important
+0x20     dword    Media_Min_W    ; Условие @media (min-width) в CSS px; 0 — нет условия
+0x24     dword    Media_Max_W    ; Условие @media (max-width) в CSS px; 0x7FFFFFFF — нет условия
```
Правила раскладываются по корзинам хэш-таблицы по самой правой части селектора: по `#id`, `.class`, тегу и корзина «прочие» (`*`). Для элемента проверяются только корзины его id, его классов и его тега. Селектор вида `.a, .b` разворачивается в два правила.

### 6.2. SEL_PART, 40 байт
Цепочка хранится справа налево — сопоставление идёт от элемента вверх к предкам.
```text
+0x00     qword    Next           ; Следующая часть цепочки
+0x08     dword    Tag_ID         ; 0 = любой тег (*)
+0x0C     dword    Combinator     ; Связь с частью Next: 0=нет (конец), 1=потомок (пробел), 2=ребенок (>), 3=тот же элемент
+0x10     qword    Id_Ptr         ; #id или 0
+0x18     dword    Id_Len
+0x1C     dword    Class_Len
+0x20     qword    Class_Ptr      ; .class или 0 (один класс на часть)
```
Составной селектор с несколькими классами (`div.a.b`) записывается несколькими частями, связанными `Combinator = 3`. Длина цепочки ограничена 32 частями.

## 7. Картинка (IMAGE)
Размер: 112 байт (`0x70`). Арена: `doc`. Одна запись на каждый `<img>` документа.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующая картинка документа (в порядке документа)
+0x08     qword    Node           ; DOM_NODE элемента <img>
+0x10     qword    Url_Ptr        ; Абсолютный URL (после выбора src / data-src / srcset)
+0x18     dword    Url_Len
+0x1C     dword    State          ; 0=Ожидает, 1=Загружается, 2=Загружена, 3=Декодирована, 4=Ошибка, 5=Пропущена
+0x20     ARENA    Data           ; Арена ресурса со сжатыми байтами файла (40 байт)
+0x48     dword    Natural_W      ; Размер оригинала (из width/height или заголовка файла)
+0x4C     dword    Natural_H
+0x50     dword    Display_W      ; Размер на экране (после вписывания в колонку и DPI)
+0x54     dword    Display_H
+0x58     qword    Pixels         ; BGRA premultiplied (VirtualAlloc) или 0
+0x60     qword    Fetch          ; Активный FETCH или 0
+0x68     dword    Last_Used      ; Номер кадра последней отрисовки (для вытеснения)
+0x6C     dword    Flags          ; IMG_SIZE_KNOWN, IMG_INLINE (≤ 64 px), IMG_DATA_URI
```
«Пропущена» — картинка внутри скрытого элемента, не больше 2×2 px (трекинг-пиксель), сверх лимитов размера или при выключенных картинках.

## 8. Сетевой запрос (FETCH)
Размер: 80 байт (`0x50`). **Статический пул из 16 слотов** на весь процесс: слот живёт дольше документа и освобождается только по событию `WINHTTP_CALLBACK_STATUS_HANDLE_CLOSING`. Адрес слота передаётся в WinHTTP как `dwContext`.

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     qword    Request          ; HINTERNET запроса
+0x08     qword    Connect          ; HINTERNET соединения
+0x10     qword    Target           ; ARENA*, в которую пишутся данные
+0x18     qword    Owner            ; DOC_CTX* (документ), IMAGE* или запись таблицы стилей
+0x20     dword    Kind             ; 0=Документ, 1=Таблица стилей, 2=Картинка
+0x24     dword    State            ; 0=Свободен, 1=Отправка, 2=Приём, 3=Готов, 4=Ошибка, 5=Закрывается
+0x28     dword    Generation       ; Номер навигации; сообщения устаревших поколений игнорируются
+0x2C     dword    Http_Status
+0x30     dword    Content_Length   ; -1, если неизвестна
+0x34     dword    Bytes_Read       ; ← пишет колбэк (READ_COMPLETE)
+0x38     dword    Win_Error        ; ← пишет колбэк (REQUEST_ERROR: dwError)
+0x3C     dword    Secure_Flags     ; ← пишет колбэк (SECURE_FAILURE)
+0x40     qword    Started_At       ; QPC-время старта (таймауты, статистика)
+0x48     qword    Reserved
```
Колбэк WinHTTP пишет **только** три помеченных поля своего слота и затем вызывает `PostMessageW(hwnd, WM_NET, индекс_слота, статус)`. Очередь сообщений гарантирует, что главный поток увидит эти записи. Итоговый URL после редиректов главный поток получает сам — `WinHttpQueryOption(WINHTTP_OPTION_URL)`, — поэтому временные строки колбэка копировать не нужно.

## 9. Строка раскладки (LINE)
Размер: 48 байт (`0x30`). Арена: `line` — **непрерывный массив** в порядке сверху вниз (Y возрастает). Видимая строка и строка под курсором находятся двоичным поиском по `Y`, строка для смещения в тексте — двоичным поиском по `Text_Start`.

```text
[Offset]  [Type]   [Field]          [Description]
+0x00     qword    First_Fragment   ; Первый FRAGMENT строки (0 для линии <hr>)
+0x08     qword    Node             ; Ближайший блочный DOM_NODE, к которому относится строка (якорь прокрутки)
+0x10     dword    Y                ; Верх строки в координатах документа
+0x14     dword    Height
+0x18     dword    Baseline         ; Смещение базовой линии от Y
+0x1C     dword    X                ; Левый край содержимого с учётом отступа (списки, цитаты)
+0x20     dword    Quote_Depth      ; Сколько полос цитаты рисовать слева
+0x24     dword    Kind             ; 0=Текст, 1=Линия <hr>, 2=Блочная картинка
+0x28     dword    Text_Start       ; Начало текста строки в буфере `text`
+0x2C     dword    Text_End
```

## 10. Фрагмент (FRAGMENT)
Размер: 48 байт (`0x30`). Арена: `layout`. Участок строки с одинаковым оформлением: несколько слов, маркер списка или картинка.

```text
[Offset]  [Type]   [Field]        [Description]
+0x00     qword    Next           ; Следующий фрагмент этой строки
+0x08     qword    Data           ; FR_IMAGE: IMAGE*; иначе — текст в буфере `text` (пробелы уже нормализованы)
+0x10     qword    Link           ; DOM_NODE ссылки <a> или 0
+0x18     dword    Text_Len       ; Длина текста (0 для картинки)
+0x1C     dword    Font_ID        ; Индекс в таблице шрифтов SysFont (размер × начертание × моноширинность)
+0x20     dword    X
+0x24     dword    Width          ; Высота и вертикальное положение — из LINE
+0x28     dword    Flags          ; FR_LINK, FR_UNDERLINE, FR_STRIKE, FR_IMAGE, FR_MUTED, FR_MARKER
+0x2C     dword    Reserved
```
Текст фрагментов лежит в буфере `text`, а не в `src`: при схлопывании пробелов исходник между словами не совпадает с отображаемым текстом. Этот же буфер — основа для Ctrl+F (совпадения через границы фрагментов и строк), выделения и копирования.

## 11. Запись истории (HISTORY_ENTRY)
Размер: 64 байта (`0x40`). Арена: `session`. Двусвязный список, не более 100 записей.

```text
+0x00     qword    Prev
+0x08     qword    Next
+0x10     qword    Url_Ptr
+0x18     qword    Title_Ptr
+0x20     dword    Url_Len
+0x24     dword    Title_Len
+0x28     dword    Anchor_Order   ; DOM_NODE.Order верхней видимой строки при уходе со страницы
+0x2C     dword    Scroll_Y       ; Запасной вариант, если якорь не найден
+0x30     qword    Cache          ; ARENA* с копией текста страницы (UTF-8) или 0
+0x38     dword    Cache_Charset
+0x3C     dword    Reserved
```
Кэш «Назад/Вперёд»: копии текста страниц хранятся в пределах **4 МБ суммарно**; при превышении вытесняются самые старые. «Назад» при наличии копии — повторный разбор из памяти (на скорости разбора это мгновенно), картинки загружаются заново. Без копии — повторная загрузка из сети.

## 12. Оценка потребления
| Сущность | Размер | На 1000 элементов |
|---|---|---|
| DOM_NODE | 72 Б | 70 КБ |
| ATTR (≈2 на элемент) | 40 Б | 78 КБ |
| LINE + FRAGMENT (≈1 строка и 3 фрагмента на элемент) | 48 + 3×48 Б | 188 КБ |

Итого около 340 КБ на 1000 элементов плюс два экземпляра текста (`src` и нормализованный `text`). Картинки ограничены бюджетом кэша пикселей (раздел 1.5) плюс сжатые файлы.
